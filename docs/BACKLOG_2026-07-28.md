## 1. Mixed feeding — a dog eats more than one food (HIGH)

### The problem

`dogs.current_food_id` is singular. Real feeding usually isn't: kibble with a wet
topper, raw with a kibble mixer, a rotation across the week, a supplement oil on top.
The single-food assumption is wrong for a large share of users, possibly most.

### Why this is not a UI change

Three layers assume one food and are wrong under mixed feeding:

- **The allergy filter.** A dog on kibble A plus topper B is exposed to everything in
  B. If B contains chicken and the filter only knows A, the dog is recorded as
  chicken-free and it isn't. This is the safety-relevant one.
- **`dog_food_switch_analyses`.** Switch detection assumes one food changing. If only
  the topper changed, the analysis attributes the outcome to the wrong variable, or
  misses the change entirely.
- **`dog_ingredient_suspects`.** Narrowing suspects across failed switches is
  meaningless if the ingredient set of the diet was never fully known.

### Proposed shape

**A diet is a flat set of components with no privileged member.** Not a main food
with extras attached. Real patterns include:

- two kibbles mixed roughly half and half
- three foods rotated across a week, none dominant
- raw four days, kibble three
- one food in the morning, a different one in the evening
- kibble with a wet topper — *one case among many, not the model*

Arbitrary N. No component is required, or allowed, to be structurally primary.

New table `dog_diet_components`:

| field | notes |
|---|---|
| `dog_id` | |
| `food_id` | nullable — freetext allowed when the food isn't in the catalogue |
| `food_freetext` | |
| `role` | **optional, descriptive only** — `topper`, `mixer`, `supplement`, `treat`. Null is normal and means "a food this dog eats". Never used in logic. |
| `share` | ordinal, nullable — see below |
| `schedule` | `every_meal`, `daily`, `specific_days`, `rotating`, `occasional` |
| `days_of_week` | nullable |
| `meal_slot` | nullable — `morning`, `evening`, `any` |
| `started_at`, `ended_at` | |

**Do not ask owners for percentages they don't know.** `share` is an ordinal —
*most of the meal / about half / a small amount / a spoonful* — never a guessed
number, and nullable throughout. Same doctrine as everywhere else.

`dogs.current_food_id` is **deprecated, not derived**. With three equal foods there
is no value it could correctly hold. Anything reading it must move to the component
set. Existing rows migrate to a single component with `role` **null** — a sole
component is not a "main", it is just the only one.

### Temporal exposure

Components need not overlap. Two foods on alternate days are both current but never
in the same bowl.

- **For allergen exposure, the union across the period is what matters.** A dog
  eating chicken on Tuesdays is exposed to chicken. Schedule does not reduce this.
- **For switch analysis, rotation is not a switch.** `dog_food_switch_analyses`
  assumes a stable baseline changing to another stable baseline. A rotating diet has
  no baseline. Detect rotation and mark those periods as unanalysable rather than
  reporting a change that didn't happen.

### Elimination trials — the case that matters most in practice

An exclusion diet trial requires a **single** component. The commonest reason trials
fail is something else being fed alongside — a treat, a chew, a topper, table scraps.

Once diets are modelled as a set, this becomes detectable: a dog flagged as on an
elimination trial with more than one active component is a trial that is not being
run cleanly. Surfacing that is genuinely useful to the practice and is only possible
under this model. Worth building as a follow-up once the set exists.

### Consequence to handle explicitly

The dog's effective ingredient set becomes the **union** of all active components.
`hardFilter` must read that union. A food with no ingredient data anywhere in the
mix means the whole diet is unconfirmable — surface that, the same way opacity is
surfaced, rather than silently filtering on a partial picture.

## 2. Stool logging — one entry per day loses the signal (HIGH)

### The problem

Stools are logged once. Dogs pass several a day and they frequently score
differently — a normal first stool and a poor second is a classic pattern, and it is
exactly the pattern that matters in food-responsive cases.

Logging once forces the owner to pick one score, which discards the two most useful
facts: **the worst score of the day** and **how many there were**.

### Proposed shape

One row per stool event, not per day:

- `dog_id`, `occurred_at` (timestamp, not date)
- `score` (existing chart scale)
- optional flags: `mucus`, `blood`, `urgency`, `straining`, `undigested_food`
- optional note

Daily figures — worst, median, count, spread — are **derived at read time, never
stored as the primary record**. Frequency per day becomes a first-class metric; it
is currently not captured at all.

### Why this matters downstream

`dog_food_switch_analyses` compares outcome metrics before and after a switch. A
single daily score is noisy and can move for reasons unrelated to diet. Worst-score
and count per day are far stronger signals, and consistency (spread within a day) is
itself clinically meaningful.

Existing single-entry rows migrate as one event each, with `occurred_at` set from
the existing date and a flag recording that the time was not captured. Do not invent
a time of day.

## 3. Mobile capture forces the camera (LOWER — but needs a decision, not just a fix)

### The problem

On mobile the label capture always opens the camera. There is no way to choose an
existing image, and no crop step before upload. A user who has a clear image already
— or who wants to crop to the composition panel — can't use it.

### The fix

The file input almost certainly carries the `capture` attribute, which forces the
camera on mobile. Removing it lets the OS offer camera *or* gallery. Add a crop step
before upload; cropping to the composition panel will also improve extraction and
reduce payload size.

### The decision that has to come first

**A screenshot from a website is not a photo of a pack**, and the difference matters:

- `ingredient_source = 'label_photo'` would be false for a website screenshot.
  Provenance must record which it is.
- More seriously, it **bypasses the domain allowlist entirely**. A user screenshotting
  a refused domain and uploading it puts that data into the catalogue through a path
  that never checks `source_domain_allowlist`. Everything built around crawl
  permissions is routed around by a screenshot.

Options:

- **(a)** Accept gallery uploads but require the user to state the source (pack /
  manufacturer website / retailer website), record it, and hold anything not from a
  pack in review rather than auto-accepting it.
- **(b)** Accept gallery uploads only for pack photos, with the prompt making that
  explicit, and treat website screenshots as out of scope.

Owner decision required before building. (a) is more useful and more honest; it
needs a new `ingredient_source` value and a provenance field.
